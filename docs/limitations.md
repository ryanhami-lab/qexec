# Limitations

QExec is a research replay engine validated on **synthetic data only**. This document states
plainly what the results do and do not mean, so no reader mistakes software validation for a
market finding.

## The headline caveat

Every number QExec produces in this build comes from a **parametric synthetic order book**, not
from any real venue. The results demonstrate that the estimation machinery runs end to end and
reports honest denominators and intervals. **They are not evidence about real markets, any real
instrument, or the profitability of any strategy.** No profitability, edge, or novelty is claimed
or implied anywhere. The real-data gate (G0) and the final real-data holdout are **blocked pending
a licensed, paid data subscription**.
The vendor decoder and real-session study entry point are also absent. Buying data alone
does not make this synthetic-only pipeline a completed real-market research result.

## Structural limitations

- **Replay counterfactual.** The engine replays an *immutable* historical tape. The hypothetical
  order is an overlay that observes the tape but never changes it. There is therefore **no market
  impact and no reactive counterparty behaviour**: real orders would move prices and alter the
  very fills being measured. Omitting impact can understate live costs; the overall bias is
  not guaranteed to have one sign because the fill and queue assumptions also matter.

- **Synthetic dynamics.** The order flow — arrivals, cancels, modifies, sweeps, the latent drift
  correlated with book imbalance, and occasional halts — is generated by a model with chosen
  parameters. Any effect QExec reports is a property of **that model**, not a market fact. A
  different generator (or real data) could change the sign or magnitude of every number.

- **FIFO (price-time) priority assumption.** Queue position and fills assume strict price-time
  priority with a single frozen ambiguity rule (a behind-order fill while quantity ahead is still
  positive yields *no* virtual fill by default, logged as `AMBIGUOUS`). Real venues may use
  pro-rata or hybrid matching, hidden/iceberg liquidity, or self-match prevention, none of which
  are modelled.

- **No real fills.** All executions are *virtual*. There is no real fill, no partial-fill
  microstructure beyond the one-contract tasks, no exchange rejection beyond the modelled status
  rules, and no acknowledgement latency beyond the constant per-scenario latency constants
  (`L0`–`L6`). Fees are applied per virtual execution from a configured constant.

- **Small session counts.** Studies here use few synthetic sessions (the quick preset uses a
  handful). Consequently many paired intervals are **wide**, and some effects are **undefined**
  (no common-completion task set) or **not estimable** (null bootstrap interval). The report
  prints these literally as `undefined` / `not estimable` and raises a **degeneracy flag** rather
  than fabricating a zero. When every observed miss is zero, the report shows the one-sided
  zero-event upper bound, never a zero-risk claim.

## Scope limitations (optional / blocked work)

- **No native C++ extension (R11, gates G3/T20/T21).** The optional native replay path is not
  built; there is no Python/C++ parity or sanitizer evidence in this build.
- **No P1 optimal-stopping policy (R12, gates GA/T27/T30/T31).** The optional P1 solver is not
  built; the comparison is limited to B0, B1, B2, B2_100MS, B3, and B3_NO_QUEUE.
- **No timezone/DST handling exercised (T51).** The synthetic feed uses an explicit integer-ns
  epoch with no daylight-saving transitions, so the UTC/DST session-assignment path is a
  real-data (G0) concern and is not exercised. Blocked pending real data.

See `docs/test_traceability.md` for the exact, honestly-marked mapping of these gaps to test IDs.

## How to read a QExec report

- The **primary paired effect** (cost) and **completion-risk** (miss difference) are shown side by
  side, each with its denominator (`n_tasks`), the number of sessions defined/undefined, and a
  bootstrap interval. A positive cost effect favours the candidate; a positive miss difference
  means the candidate misses *more* (worse).
- A **degeneracy flag** means the pair has no common-completion set: no cost effect is estimable,
  and this is reported as a count, not as zero.
- The **epsilon sensitivity** table is explicitly **decision-only**: it recomputes action shares
  as epsilon varies but does *not* claim realized outcomes for non-primary epsilons (those would
  require a full replay).

Saved output hashes and append-only application logging detect accidental drift and preserve
ordinary run history. They are local files, not cryptographic signatures or access controls;
an operator with write access can rewrite a study outside the application. Reusing a nonempty
run directory is refused, and interrupted runs require a fresh output directory.
